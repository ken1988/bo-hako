# 開発画面の設定項目整理案

## 結論

開発画面は「機能を追加した順に縦へ並べる」構成から、**利用頻度と目的で分けた4つの画面内タブ**へ整理する。

1. **日常操作** — ニュース、コメント、貿易予約と予約一覧
2. **国家設定** — 国名、首都名、元首名、国旗、パスワード
3. **関連リンク** — Wiki、貿易情報、報道機関、Slack
4. **表示設定** — スタイルシート

ニュース、コメント、貿易予約はいずれも適宜入力する可能性があるため、別々のタブへ分断せず初期表示の「日常操作」へ集約する。その中では想定利用頻度に合わせて **ニュース → コメント → 貿易予約** の順に到達しやすくするが、3機能の視覚的な強さに大きな差は付けない。

タブを切り替えても入力途中の値を失わないよう、すべてを同一ページ内に残す。JavaScriptが無効な場合は、全項目を同じ順番で縦に表示する。

## 1. 現状の課題

提供された画面と現行テンプレートから、次の問題がある。

- 日常的に使うニュース、コメント、貿易予約と、めったに使わない国名・スタイル変更が同じ強さで並んでいる。
- 「コメント更新」「ニュース更新」「首都名入力」など、見出しがすべて同じ見た目で重要度を判断しにくい。
- Wiki、貿易情報、報道機関のURLは目的が近いのに、それぞれ独立した欄と更新ボタンを持つ。
- 国名、首都名、元首名、パスワードが離れており、「国家プロフィールの編集」というまとまりが見えない。
- 2カラムは画面幅を使えている一方、左右の内容に意味的な対応がなく、どこを見ればよいか予測しにくい。
- 説明文や注意書きが常時大きな面積を占め、実際の入力欄を探しにくい。
- 各フォームの保存単位や、保存済み・未保存の状態が分かりにくい。

## 2. 推奨する情報設計

### 2.1 項目の分類

| タブ | 収録する項目 | 利用頻度 | 方針 |
|---|---|---:|---|
| 日常操作 | ニュース、コメント、貿易予約、予約一覧、収支レポート | 高 | 最初に表示し、3つの入力機能を画面遷移なしで使えるようにする |
| 国家設定 | 国名、パスワード、首都名、元首名、国旗 | 低 | 「基本情報」「セキュリティ」「画像」の小見出しで分ける |
| 関連リンク | Wiki、貿易情報、報道機関、Slack | 中〜低 | URL設定を一か所にまとめ、Slackはコミュニティ導線として分ける |
| 表示設定 | スタイルシート | 低 | 通常操作から離す。ローカル画像設定は廃止する |

「日常操作」は設定ではなく主要作業なので、他の設定群とは明確に分離する。タブ名に抽象的な「一般」「詳細」は使わず、中身を予想できる名称にする。

### 2.2 デスクトップの配置

```text
┌──────────────────────────────────────────────────────────┐
│ 開発画面  ノイエクルス自由国                    保存状態 │
├──────────┬────────┬──────────┬───────────────┤
│ 日常操作   │ 国家設定 │ 関連リンク │ 表示設定        │
├───────────────────────────────┬──────────────────────────┤
│ ニュース投稿                    │ コメント                 │
│ [カテゴリ] [発表者] [内容]       │ [コメント入力欄] [保存]  │
├───────────────────────────────┼──────────────────────────┤
│ 貿易予約                        │ 予約一覧                 │
│ [相手国] [種類] [数量] [予約]   │ 1  …              [取消]│
├───────────────────────────────┴──────────────────────────┤
│ 収支レポート（初期状態は閉じる）                         │
└──────────────────────────────────────────────────────────┘
```

- ページ幅は `max-width: 1200px` 程度に制限し、広い画面で左右へ離れすぎないようにする。
- 上段へニュースとコメント、下段へ貿易予約とその結果である予約一覧を置く。3つの日常操作をタブ移動なしで利用できることを優先する。
- 予約一覧は表のヘッダーを固定し、件数が多い場合だけ一覧内をスクロールさせる。
- 収支レポートは必要時だけ参照する情報なので初期状態を閉じる。開いたときに当期収支、残高、内訳をまとめて表示する。

### 2.3 モバイルの配置

- 画面内タブは横スクロール可能にし、常に現在のタブ名を表示する。
- 「日常操作」は **ニュース → コメント → 貿易予約 → 予約一覧 → 収支** の1カラムにする。
- 予約一覧は横長の表ではなく、1予約1カードにする。
- 主要な投稿・保存・予約ボタンは各フォーム末尾で全幅にする。
- タップ領域は最低44px、入力欄の文字サイズは16px以上を目安にする。

## 3. 各タブの具体案

### 3.1 日常操作

- ニュース、コメント、貿易予約はどれも適宜使われるため、同じタブ内に置く。想定頻度はニュース、コメント、貿易予約の順だが、見出しやカードの視覚的な強さは揃える。
- ニュースとコメントはデスクトップで横並び、モバイルでは利用頻度順の縦並びにする。
- 文字数は入力欄の右下に `24 / 100` の形式で表示し、残量が少ないときだけ強調する。
- ニュース投稿回数は投稿ボタンの近くに置き、投稿できない場合は理由を示す。
- 貿易予約には「予約可能件数 10件中9件」のような状態を表示する。
- 貿易入力は「相手」「何を」「数量」の自然な順に並べ、単位を入力欄の外へ固定表示する。
- 実行可能な操作だけを候補に出す。選べない操作を残す場合は、無効理由を併記する。
- 予約一覧のラジオボタンによる中止操作は、各行の「取り消す」ボタンへ変更する。
- 複数件をまとめて処理する必要がある場合のみ、チェックボックスと一括操作を用意する。
- 削除・中止は通常の橙色ではなく危険色にし、対象を確認できる文言にする。

### 3.2 国家設定

- 国名、首都名、元首名を「基本情報」にまとめ、国名とパスワードは別々のフォームで変更できるようにする。
- 国名変更の費用は国名欄の直下へ置き、送信直前にも確認を出す。
- パスワード変更は独立した「セキュリティ」カードにし、新パスワードの確認入力を追加する。
- 国旗は現在画像のプレビュー、ファイル選択、制約、保存ボタンの順にする。
- PNG/JPEG、64KB、変換後サイズなどの詳細は「アップロード条件」へ折りたたむ。エラーは該当入力の直下に表示する。
- 開発画面への入場時点で認証済みなので、国名変更やパスワード変更の前に再認証は求めない。
- 既存バックエンドとの互換性のため、各フォームには認証済みの現在のパスワードをhiddenフィールドで引き続き送信する。

hiddenフィールドは秘匿機能ではなく、ブラウザの開発者ツールから値を参照できる。したがって通信はHTTPSを前提とし、値を画面表示やログへ出さず、HTML属性として安全にエスケープし、サーバー側でも従来どおり検証する。

### 3.3 関連リンク

- 3種類の外部URLは「関連リンク」という1枚のカードに統合する。
- カード下部の「すべて保存」に加え、各URLの横にも「このリンクを保存」を置き、一括保存と個別保存の両方を可能にする。
- 個別保存後に、同じカード内の未保存入力を消したり古い値へ戻したりしない。
- URLの横に「リンクを開く」を置き、保存前後に遷移先を確認できるようにする。
- Slack登録は設定フォームではないため、同じタブ下部の「コミュニティ」カードへ移す。

### 3.4 表示設定とローカル画像設定の廃止

- スタイルは名称だけでなく、小さな配色プレビューを並べて選択可能にする。
- 現行のローカル画像設定は画面・入力処理・Cookie処理から廃止した。保存済みの `IMG` Cookieがある場合も参照せず、通常の画像ディレクトリへフォールバックする。

「対応環境が限られる」とした理由は、現行機能がファイルをサーバーへアップロードするのではなく、`<input type="file">` で選んだ利用者PC上のパスを `IMGLINE` として保存し、そのパスから画像を読み込む古い方式だからである。現在の一般的なブラウザでは次の制約がある。

- プライバシー保護のため、file inputから実際の絶対パスは取得できず、`C:\fakepath\...` のような仮の値になる。
- Webページから利用者PC上の任意の `file://` URLを継続的に参照することは、オリジン分離とローカルファイル保護により制限される。
- 保存したパスはその端末・フォルダ構成にしか存在せず、別端末、スマートフォン、フォルダ移動後には利用できない。
- サーバーから配信する画像と違ってキャッシュや更新をサイト側で管理できず、表示不良をサポートしにくい。

そのため「上級者向け」として残しても安定した機能にはならず、設定項目を減らす今回の目的にも合う廃止が妥当である。

## 4. 共通UIルール

### 保存単位

- 基本はカード単位で保存し、ボタン名を「更新」ではなく「コメントを保存」「基本情報を保存」のように具体化する。
- 関連リンクは3項目の一括保存と、変更した1項目だけの個別保存の両方を提供する。
- 保存後はカード上部に「保存しました」と表示し、ページ先頭へ移動させない。
- 未保存の変更がある状態でタブ移動・離脱する場合は確認する。

### 見出しと説明

- `h1`: 開発画面、`h2`: タブ内の主要カード、`h3`: カード内の小分類、の順を守る。
- 説明は入力ラベルの近くに短く置き、長い仕様は「詳しい条件」へ格納する。
- 必須・任意、文字数、単位、費用をラベル付近へ一貫して表示する。

### アクセシビリティ

- 色だけで成功・警告・エラーを表さず、アイコンと文言を併用する。
- すべての入力と `label` を関連付け、キーボードでタブとフォームを操作可能にする。
- タブには `role="tablist"`、`role="tab"`、`aria-selected`、対応する `aria-controls` を付ける。
- フォーカス表示を消さず、本文・入力・ボタンはWCAG 2.2 AA相当のコントラストを目標にする。

## 5. 段階的な実装順

既存フォームの送信先や処理を一度に変えず、次の順で進めると安全である。

1. **分類だけ行う（実装済み）** — 現在のフォームを4グループとして識別できるセクションで囲み、ページ内ナビゲーションを追加する。
2. **視覚階層を整える（実装済み）** — 最大幅、カード、余白、見出し、ボタン文言を統一する。
3. **タブ化する（実装済み）** — JavaScript有効時だけタブ表示にし、無効時は全セクションを縦に表示する。
4. **重複フォームを統合する（実装済み）** — 3種類の関連リンクへ一括・個別保存の両方を用意し、ローカル画像設定を廃止する。
5. **操作フィードバックを追加する** — インラインの検証、保存完了、未保存警告を実装する。
6. **利用状況を確認する** — 各機能の利用回数、完了時間、エラーを比較し、初期画面内の配置を調整する。

### 実装対象ファイル

| ファイル | 担当する内容 |
|---|---|
| `trade/hako-html.php` | 開発画面全体、貿易予約、収支、国名・元首名・パスワード、表示設定の出力とページ内ナビゲーション |
| `trade/templates/banners.html` | ニュース、コメント、首都、国旗、関連リンク、Slackのフォーム分類と関連リンク統合フォーム |
| `trade/css/nd_flat.css` | ND Flatテーマの分類ナビゲーション、カード、レスポンシブ表示 |
| `trade/css/nd_flat-blue.css` | ND Flat Blueテーマの分類ナビゲーション、カード、レスポンシブ表示 |
| `trade/css/nd_flat-grey.css` | ND Flat Greyテーマの分類ナビゲーション、カード、レスポンシブ表示 |
| `trade/owner-tabs.js` | JavaScript有効時のタブ切り替えとキーボード操作 |
| `trade/hako-turn.php` | 関連リンクの個別・一括保存処理 |
| `trade/hako-main.php` | 廃止したローカル画像設定の入力・Cookie処理の撤去 |

実装順4まで完了し、カードによる視覚階層、段階的に有効になるタブ、関連リンクの個別・一括保存、ローカル画像設定の廃止を反映した。JavaScriptが無効な場合は、4分類を縦に並べてすべて表示する。

## 6. 最初のリリースの受け入れ基準

- 初期表示からニュース投稿、コメント保存、貿易予約のすべてへ、タブ移動せず到達できる。
- すべての現行機能が4タブのいずれかに属し、同じ機能が複数箇所に現れない。
- 収支レポートは初期状態で閉じており、必要時にキーボードでも展開できる。
- 関連リンクは3件の一括保存と1件ごとの個別保存ができる。
- デスクトップでは主要作業領域が中央寄せされ、左右のカラムに意味的な対応がある。
- 360px幅でページ全体に意図しない横スクロールが発生しない。
- JavaScript無効時も全フォームへ到達できる。
- 保存・失敗・未保存の状態を、色だけに頼らず認識できる。
- キーボードのみでタブ移動、入力、保存、予約取り消しができる。
- 再認証を追加せず、必要なフォームでは既存バックエンド向けのパスワード値が安全に送信される。
- ローカル画像設定が画面に表示されず、保存済み設定がある利用者にも通常画像が表示される。

## 7. 確定した前提

- 想定利用頻度はニュース、コメント、貿易予約の順。ただし、いずれも日常的に入力し得るため同じ初期タブに置く。
- 収支レポートは必要時だけ参照するため、日常操作タブの末尾で初期状態を閉じる。
- 3種類の関連リンクは一括保存と個別保存の両方を可能にする。
- ローカル画像設定は廃止する。
- 開発画面内で再認証は求めない。バックエンド処理に必要な現在のパスワードは、既存どおり各フォームのhiddenフィールドで送信する。

この前提で、まず分類と視覚階層のみを反映した試作を作り、ニュース、コメント、貿易予約のいずれにも素早く到達できるかを検証する。
